2. A QUE BASE SE CONECTA REALMENTE EL BACKEND
============================================================================

El pool de map-service.js (linea 11-20) lee process.env.DB_NAME.
Como .env define DB_NAME=mapa_navegacion, el backend se conecta a mapa_navegacion.

El texto del log de arranque (linea 25):
  console.log('[map-service] Conectado a PostGIS (mapa_local)');

Es un STRING HARDCODEADO. No refleja el nombre real de la base.
El log deberia decir "mapa_navegacion" pero dice "mapa_local" porque
el string nunca se actualizo cuando se cambio la base.

CONCLUSION: el backend SE CONECTA a mapa_navegacion, el log miente.
El fallback 'mapa_local' en linea 14 nunca se activa porque .env
siempre tiene DB_NAME seteado.

VEREDICTO
============================================================================

El backend SI esta leyendo la geometria correcta (v2, con buffer) de
mapa_navegacion. El texto "mapa_local" en el log de arranque es un string
hardcodeado que NO refleja la base real — es un vestigio de cuando la base
se llamaba asi (o un nombre de desarrollo que nunca se actualizo en el log).

No hay una base "mapa_local" en PostgreSQL. Si se quitara DB_NAME del .env,
map-service.js fallaria al intentar conectarse a "mapa_local" (no existe),
mientras que sitport-routes.js y puertos-service.js seguirian funcionando
(su fallback es 'mapa_navegacion' que si existe).

RIESGOS IDENTIFICADOS:
  1. El fallback de map-service.js:14 ('mapa_local') es incorrecto y
     deberia ser 'mapa_navegacion' como el resto de los archivos.
  2. El log hardcodeado en map-service.js:25 es confuso/engañoso.
  Ambos son cosmeticos mientras .env tenga DB_NAME, pero son bombas
  de tiempo si .env se pierde o se despliega sin esa variable.
